# 실제 사이버공격 사례 기반 멀티클라우드 보안 아키텍처 설계

**문서 유형:** Security Architecture / Threat Modeling / Incident Analysis  
**작성 기준일:** 2026-11-02  
**상태:** 설계 및 구현 기준 제안  
**대상:** 프로덕션급 멀티클라우드 관리·마이그레이션 플랫폼

---

# 1. 개요

## 1.1. 문서 목적

본 문서는 최근 발생한 사이버 침해사고와 AI를 활용한 공격 사례를 분석하고, 공격 원인·침투 경로·피해·기업 대응을 기반으로 프로덕션급 멀티클라우드 관리 및 마이그레이션 플랫폼에 적용할 보안 아키텍처를 정의한다.

단순히 WAF, IAM, 암호화, AI 탐지 기능을 도입하는 것이 아니라 다음을 명확하게 설명하고 검증하는 것을 목표로 한다.

1. 실제로 어떤 사이버공격이 발생했는가?
2. 공격자는 어떠한 경로와 취약점을 이용했는가?
3. 어떤 데이터와 시스템이 피해를 입었는가?
4. 피해 기업과 보안기관은 어떻게 대응했는가?
5. 동일한 공격이 멀티클라우드 관리 플랫폼에서 발생할 경우 어떤 위험이 존재하는가?
6. 해당 위험을 방지하기 위해 어떤 아키텍처와 통제를 적용해야 하는가?
7. 설계한 통제가 실제로 작동하는지 어떻게 검증할 것인가?

본 문서는 다음 원칙을 따른다.

- **실제 사고 기반 설계:** 공개된 침해사고, 기술 분석, 보안 권고를 근거로 위협 모델 수립
- **최소 권한:** 사용자, AI, 서비스, 에이전트에 필요한 최소 권한만 부여
- **다중 방어:** 예방 통제가 실패하더라도 탐지·격리·복구가 가능하도록 설계
- **실행 통제:** AI의 제안을 실제 운영 권한과 분리
- **실측 검증:** 보안 통제가 존재한다는 사실보다 실제 공격·장애 시험에서의 결과를 중시
- **실패 시 안전한 상태 유지:** 확인되지 않은 실행이나 변경을 성공으로 간주하지 않음
- **환경 간 일관성:** AWS, Google Cloud, 온프레미스에서 공통 보안 요구를 유지
- **증거 기반 운영:** 실행·승인·정책 판단·복구 결과를 감사 가능한 형태로 기록

## 1.2. 보안 설계의 핵심 방향

멀티클라우드 관리 플랫폼은 일반적인 웹 애플리케이션과 다른 위험을 가진다.

관리 플랫폼은 여러 조직의 클라우드 계정, 운영 서버, 데이터베이스, 소스 코드, 배포 권한에 접근할 수 있다.

따라서 플랫폼 자체가 침해될 경우 피해가 하나의 애플리케이션을 넘어 여러 클라우드 환경으로 확산될 수 있다.

이러한 특성에 따라 다음 세 가지를 핵심 보안 목표로 정의한다.

### SG-1. Compromise Containment — 침해 범위 제한

일부 구성 요소가 침해되더라도 다른 조직, 애플리케이션, 클라우드 계정으로 공격이 확산되지 않도록 한다.

### SG-2. Evidence-Based Execution — 증거 기반 실행

AI의 판단이나 단순 API 성공 응답만을 신뢰하지 않고, 정책·승인·실제 리소스 상태·데이터 검증 결과를 확인한 후 실행과 완료를 판정한다.

### SG-3. Recoverable Migration — 복구 가능한 이전

마이그레이션과 운영 변경이 실패하더라도 중복 실행, 데이터 분기, 백업 손상을 방지하고 검증된 복구 경로를 제공한다.

# 2. 사이버공격 범주 및 위협 모델

## 2.1. 주요 공격 유형

| 공격 범주 | 세부 공격 방식 | 주요 공격 대상 | 예상 피해 |
|---|---|---|---|
| 웹 애플리케이션 | XSS, SQL Injection, SSRF, CSRF | Web UI, API, 세션 | 계정 탈취, 무단 요청, 데이터 유출 |
| 인증·권한 | OAuth 토큰 탈취, 피싱, 권한 상승 | OIDC, IAM, AssumeRole | 클라우드 계정 침해 |
| API·네트워크 | DDoS, API 남용, 스캐닝 | ALB, Gateway, Worker | 서비스 중단, 비용 증가 |
| 공급망 | npm 악성 패키지, CI/CD 침해 | 빌드 환경, 레지스트리 | 악성코드 실행, 자격증명 탈취 |
| 서버·클라우드 | RCE, 웹셸, 측면 이동 | 관리 노드, 에이전트 | 운영 시스템 침해 |
| 랜섬웨어 | 데이터 암호화, 백업 삭제 | DB, 스토리지, 백업 | 서비스 중단, 데이터 손실 |
| AI 기반 공격 | Agentic Hacking, Prompt Injection | AI 에이전트, 실행 도구 | 자동화된 권한 오용 |
| 마이그레이션 | 복제 경로 탈취, 데이터 조작 | CDC, DB, 트래픽 전환 | 데이터 불일치, 유출, 운영 중단 |
| 멀티테넌시 | IDOR, BOLA, 조직 경계 우회 | API, DB, Cloud Adapter | 다른 고객 데이터·리소스 접근 |
| 감사·복구 | 로그 변조, 백업 파괴 | 감사 저장소, 복구 자산 | 사고 조사·복구 실패 |

# 3. 실제 사이버 침해사고 분석

## 3.1. SK텔레콤 유심 정보 유출 — 내부망 침투와 측면 이동

**발생:** 2025년 4월 공개, 2025년 7월 정부 최종 조사  
**공격 유형:** 악성코드, 계정 탈취, 내부망 침투, 측면 이동, 데이터 유출

### 사건 개요

SK텔레콤 침해사고에서는 통신 가입자 인증과 관련된 유심정보가 유출되었다.

정부 최종 조사에서 약 2,696만 건의 IMSI 기록 유출, 28대의 감염 서버, 33종의 악성코드가 확인되었다.

공격은 단일 서버에서 끝나지 않고 관리망과 인증 시스템으로 확대되었다.

### 확인된 공격 경로

```text
공격자가 확보한 계정정보
    ↓
내부 관리망 접근
    ↓
여러 서버에 악성코드 설치
    ↓
음성통화 인증 시스템 접근
    ↓
유심정보 확보
    ↓
외부 통신 접점을 통한 정보 유출
```

정부 조사에서는 평문 계정정보 보관, 이전 침해사고 대응 미흡, 중요 정보 보호 수준 미흡 등이 지적되었다.

다만 최초 침투의 모든 세부 단계가 공개적으로 완전히 규명된 것은 아니므로 특정 초기 취약점 하나를 확정적인 원인으로 단정하지 않는다.

### 피해

- 대규모 유심 관련 가입자 인증정보 유출
- 내부 관리망과 주요 인증 시스템 침해
- 악성코드 감염 서버 다수 확인
- 통신 이용자 보호 조치 및 대규모 대응 비용 발생
- 기업 신뢰도와 보안 거버넌스에 대한 문제 제기

### 실제 기업·기관 대응

- 의심 서버 격리 및 악성코드 제거
- 비정상 이용 탐지 체계 강화
- 유심 교체 및 유심 보호 서비스 제공
- 내부 인증·계정관리 보안 강화
- 관리망 분리와 중요 정보 보호체계 점검
- 정부 차원의 보안 개선 요구

### 아키텍처 반영 — CTRL-01: Lateral Movement Containment

**설계 근거:** 공격자가 한 서버나 관리 계정을 장악했더라도 다른 애플리케이션과 클라우드 계정으로 피해가 확산되지 않아야 한다.

**적용 통제**

1. 운영 클라우드의 장기 자격증명을 온프레미스 에이전트에 저장하지 않는다.
2. 에이전트별로 고유한 워크로드 신원을 발급한다.
3. 조직·애플리케이션·작업 단위로 실행 권한을 분리한다.
4. 관리망, 배포망, 검증망, 데이터망의 네트워크 접근 경계를 분리한다.
5. DB와 관리 API는 기본적으로 공개 인터넷에 노출하지 않는다.
6. 에이전트가 허용된 대상과 명령만 실행하도록 제한한다.
7. 침해가 의심되는 에이전트의 인증서를 폐기하고 신규 작업을 중단한다.
8. 노드 침해가 확인되면 단순 프로세스 재시작이 아니라 재구축·재등록을 요구한다.

**검증 시나리오**

- 조직 A의 에이전트가 조직 B의 리소스 접근 시도
- 동일 조직 내 다른 애플리케이션의 DB 접근 시도
- 폐기된 에이전트 인증서로 재접속 시도
- 에이전트 격리 이후 다른 애플리케이션의 정상 운영 확인

**성공 기준:** 침해된 구성 요소의 권한이 허용 범위 밖으로 확장되지 않아야 한다.

**참고:** 과학기술정보통신부 2025년 7월 최종 조사 발표 및 관련 공식 보안 개선 자료

## 3.2. Salesloft Drift–Salesforce — OAuth 토큰 기반 공급망 침해

**발생:** 2025년 8월  
**공격 유형:** SaaS 공급망 침해, OAuth 자격증명 탈취, API 데이터 유출

### 사건 개요

Salesloft Drift 통합 환경에서 발생한 자격증명 침해로, 연결된 고객사의 Salesforce 환경에 대한 무단 접근이 발생했다.

공격자는 정상적으로 발급된 OAuth 토큰을 이용해 고객 데이터를 조회·반출했다.

Google Threat Intelligence Group은 공격자가 반출 데이터에서 AWS 자격증명, 비밀번호, Snowflake 토큰 등 추가 비밀정보를 탐색했다고 보고했다.

### 공격 경로

```text
제3자 SaaS 통합 서비스 침해
    ↓
OAuth 토큰 확보
    ↓
정상적인 Salesforce API 인증
    ↓
권한이 허용한 범위 내 대량 데이터 조회
    ↓
고객 데이터 외부 반출
    ↓
반출 자료에서 추가 인증정보 탐색
```

이 사례의 중요한 특징은 공격자가 매번 새로운 기술적 취약점을 이용하지 않아도 유효한 자격증명만으로 정상 API를 악용할 수 있다는 점이다.

### 피해

- 고객사의 Salesforce 지원·영업 관련 데이터 노출
- 지원 기록에 포함된 비밀정보 유출 위험
- 다수 기업의 자격증명 회전 및 외부 연결 재검토 필요
- 제3자 서비스 연결을 통한 연쇄적인 위험 노출

### 기업 대응

Cloudflare 등 영향을 받은 기업들은 다음 대응을 공개했다.

- 문제가 발생한 제3자 통합 연결 차단
- 관련 OAuth 자격증명 폐기
- 접근 권한 및 외부 통합 서비스 점검
- 노출 가능성이 있는 비밀정보 회전
- 침해 범위 조사 및 고객 통지

### 아키텍처 반영 — CTRL-02: Federated Credential Isolation

**설계 근거:** 유효한 인증 토큰이 사용됐다는 사실만으로 안전한 요청이라고 판단해서는 안 된다.

**적용 통제**

| 통제 영역 | 적용 방식 |
|---|---|
| AWS 인증 | STS AssumeRole |
| GCP 인증 | Workload Identity Federation |
| 장기 자격증명 | 고객 Access Key 저장 최소화·원칙적 금지 |
| 권한 범위 | 조직·앱·작업 범위로 제한 |
| 실행 식별 | SourceIdentity, 세션 태그, Operation ID |
| 권한 수명 | 필요한 최소 세션 기간 |
| 비밀 저장 | Secrets Manager·OpenBao 등 참조 기반 |
| 감사 | 클라우드 API 호출과 내부 작업 ID 연관 |
| 사고 대응 | 연결 단위 권한 폐기, 세션 차단, 영향 조사 |

AWS의 STS 임시 자격증명은 모든 상황에서 즉시 삭제되는 방식이 아니므로, 세션 무효화 정책과 전파 지연까지 실제로 검증해야 한다.

**검증 시나리오**

조직 A의 실행 권한을 탈취했다고 가정한 테스트 주체가 조직 B의 리소스를 조회·변경하려고 시도한다.

**성공 기준:** 서버 인가 또는 클라우드 IAM 수준에서 요청이 거부되어야 한다.

**참고:** Google Threat Intelligence Group의 2025년 UNC6395 조사, Cloudflare 침해사고 공개자료

## 3.3. Shai-Hulud — npm 소프트웨어 공급망 공격

**발생:** 2025년 하반기 및 이후 관련 변종  
**공격 유형:** 악성 npm 패키지, 패키지 설치 스크립트, 자격증명 수집, 공급망 확산

### 사건 개요

정상적으로 사용되던 npm 패키지에 악성코드가 포함되면서 개발자의 로컬 환경과 CI/CD 파이프라인이 공격 표면으로 사용되었다.

CISA는 2025년 공격에서 500개 이상의 npm 패키지가 손상됐다고 설명했다.

공격자는 패키지 설치 과정에서 실행되는 코드를 이용하여 개발 환경의 토큰과 클라우드 자격증명을 수집하고, 탈취한 게시 권한을 악용해 추가 패키지로 확산시키려 했다.

### 공격 경로

```text
패키지 유지관리 계정 침해 또는 악성 패키지 배포
    ↓
개발자 또는 CI 환경에서 패키지 설치
    ↓
설치 단계의 스크립트 실행
    ↓
환경변수·파일·토큰 탐색
    ↓
클라우드 및 GitHub 자격증명 수집
    ↓
외부 유출 또는 추가 패키지 오염
```

### 피해

- 개발자 인증정보 탈취
- CI/CD 실행 환경 침해
- GitHub 저장소와 패키지 게시 권한 노출
- 여러 프로젝트로 악성 의존성 전파
- 클라우드 환경으로의 추가 침해 가능성

### 기업·기관 대응

- 손상된 패키지 버전 제거
- 개발 및 CI 자격증명 회전
- 패키지 잠금 파일과 의존성 검증 강화
- 공급망 침해 지표 분석
- 조직 단위 패키지 사용 감사
- 빌드·배포 권한 분리 권고

### 아키텍처 반영 — CTRL-03: Zero-Credential Build Sandbox

**설계 근거:** 사용자 코드를 빌드하는 환경은 신뢰된 코드 실행 환경으로 취급해서는 안 된다.

**적용 통제**

1. 빌드마다 일회성 격리 VM 또는 동등한 강도의 샌드박스를 생성한다.
2. 빌드 환경에 운영용 AWS/GCP 자격증명을 전달하지 않는다.
3. 빌드 환경의 외부 통신은 기본적으로 차단한다.
4. 필요한 패키지 저장소에 한해 통제된 프록시를 통한 접근을 허용한다.
5. lockfile과 고정된 베이스 이미지로 재현성을 높인다.
6. SBOM을 생성해 사용된 의존성을 기록한다.
7. 취약점 및 악성코드 검사를 수행한다.
8. 빌드된 이미지의 digest를 고정한다.
9. 신뢰된 서명 단계에서 이미지를 서명한다.
10. 배포 시 서명·digest·승인된 출처를 검증한다.
11. 빌드 실행자와 운영 배포 실행자를 별도 권한 주체로 분리한다.

**주의:** lockfile, SBOM, 이미지 서명만으로 악성 패키지를 완전히 방지할 수는 없다. 악성코드 실행으로 인한 피해 제한은 실제 실행 격리와 네트워크·자격증명 통제로 구현해야 한다.

**검증 시나리오**

안전하게 모사한 악성 패키지가 빌드 과정에서 통제된 외부 수집 서버, 클라우드 메타데이터, 운영 인증정보에 접근하도록 시도한다.

**성공 기준:** 운영 비밀 접근이 불가능하고 허용되지 않은 통신이 차단되어야 한다.

**참고:** CISA Shai-Hulud 공급망 보안 권고, Microsoft Security 분석

## 3.4. Microsoft SharePoint ToolShell — 인증 우회와 원격 코드 실행

**발생:** 2025년 7월  
**공격 유형:** 인증 우회, 역직렬화 취약점, RCE, 웹셸, 측면 이동, 랜섬웨어

### 사건 개요

인터넷에 노출된 온프레미스 SharePoint 서버의 취약점 체인을 이용한 공격이 발생했다.

공격자는 인증 우회 및 원격 코드 실행을 통해 웹셸 설치, 서버 암호화 키 탈취, 지속 접근, 내부 이동을 시도했다.

일부 공격에서는 랜섬웨어 배포도 관측되었다.

### 공격 경로

```text
취약한 인터넷 공개 SharePoint 서버
    ↓
인증 우회 및 역직렬화 취약점 악용
    ↓
원격 코드 실행
    ↓
웹셸 설치
    ↓
서버 암호화 키·인증정보 접근
    ↓
지속 접근 및 측면 이동
    ↓
추가 시스템 침해 또는 랜섬웨어 배포
```

### 피해

- 온프레미스 서버 침해
- 서버 인증정보 및 암호화 키 노출
- 내부 시스템으로 공격 확산
- 업무 서비스 중단 및 데이터 암호화 위험

### 기업·기관 대응

- 긴급 보안 업데이트
- 침해 지표 확인 및 웹셸 탐지
- 악성 파일과 지속 접근 수단 제거
- 서버 격리·재구축
- 암호화 키 회전
- 추가 감염 장비 조사

이미 침해된 서버는 보안 패치만 적용해도 웹셸과 탈취 자격증명 문제가 해결된다고 보장할 수 없다.

### 아키텍처 반영 — CTRL-04: Compromised Agent Recovery

**설계 근거:** 온프레미스 관리 에이전트 자체가 침해될 수 있음을 전제로 설계한다.

**적용 통제**

- 외부에서 에이전트로 접근하는 관리 포트를 기본적으로 열지 않는다.
- 에이전트가 제어면으로 외향 mTLS 연결을 설정한다.
- SPIFFE/SPIRE 등으로 워크로드 신원을 관리한다.
- 단기 X.509 인증서를 발급하고 신원 폐기를 지원한다.
- 에이전트를 비루트 권한으로 실행한다.
- 실제 변경 작업은 제한된 별도 실행자에게 위임한다.
- 명령 종류·인자·대상 경로·리소스 범위를 검증한다.
- 노드 무결성 위반 시 신규 변경 작업을 차단한다.
- 침해 노드는 재구축 및 재등록을 거쳐 신뢰를 회복한다.

mTLS는 연결 상대의 신원을 검증하지만, 이미 침해된 에이전트의 정상 권한 오용까지 방지하지는 못한다. 추가적인 실행 통제와 워크로드 격리가 필요하다.

**검증 시나리오**

- 폐기된 인증서로 재접속
- 승인되지 않은 명령 실행 요청
- 다른 애플리케이션 접근
- 에이전트 격리 후 서비스 연속성 확인

**참고:** Microsoft ToolShell 보안 분석, CISA 및 Singapore CSA 권고

## 3.5. AWS Ops Wheel — Stored XSS 및 세션 탈취 위험

**공개:** 2026년 7월 31일  
**취약점:** CVE-2026-18481  
**공격 유형:** Stored XSS, 위험 URL 렌더링, 인증 세션 탈취 가능성

### 사건 개요

AWS 오픈소스 운영 도구 Ops Wheel에서 URL 입력값 검증 및 렌더링 문제로 Stored XSS 취약점이 공개되었다.

권한이 있는 사용자가 위험한 URL을 저장하면 다른 사용자의 인증된 브라우저 환경에서 스크립트가 실행될 가능성이 있었다.

이는 실제 대규모 침해 피해가 확인된 사례가 아니라 공개된 보안 취약점과 잠재적인 공격 경로다.

### 공격 경로

```text
조작된 URL 또는 입력값 등록
    ↓
운영 관리 UI에 저장
    ↓
관리자가 해당 UI 조회
    ↓
브라우저에서 비신뢰 스크립트 실행 가능성
    ↓
세션 탈취 또는 관리자 권한 오용 위험
```

### 플랫폼 적용 위험

동일한 공격이 발생할 수 있는 입력 지점은 다음과 같다.

- GitHub 저장소 URL
- 클라우드 연결 이름 및 설명
- 배포 로그
- AI 분석 보고서
- 애플리케이션 오류 메시지
- 외부 데이터에서 수집한 메타데이터
- 변경 diff 및 마이그레이션 보고서

### 아키텍처 반영 — CTRL-05: Web Session and Output Isolation

| 통제 | 구현 방식 |
|---|---|
| XSS 방어 | React 기본 이스케이핑 유지 |
| HTML 렌더링 | 임의 HTML 렌더링 금지 또는 검증된 Sanitizer 사용 |
| URL 검증 | 허용된 프로토콜·도메인 정책 |
| 세션 보호 | HttpOnly·Secure 쿠키 |
| CSRF 방어 | SameSite 및 CSRF 토큰·Origin 검사 |
| CSP | nonce 기반 스크립트 제한 |
| API 인가 | 서버 측 객체별 접근 권한 검증 |
| 중요 작업 | 재인증·승인·감사 |
| 외부 콘텐츠 | 비신뢰 데이터로 취급 |

### 검증 시나리오

로그, 설명, URL, AI 보고서에 HTML·스크립트·위험 URL이 포함된 경우에도 관리자 브라우저에서 임의 스크립트가 실행되지 않아야 한다.

**참고:** AWS Security Bulletin CVE-2026-18481

## 3.6. Marks & Spencer — 랜섬웨어와 대규모 운영 중단

**발생:** 2025년 4월  
**공격 유형:** 사회공학, 제3자 접근 침해 의혹, 랜섬웨어, 운영 중단

### 사건 개요

영국 유통기업 Marks & Spencer는 사이버공격 이후 온라인 주문을 중단하고 일부 업무를 수동 절차로 전환했다.

2026년 연차보고서에는 직접적인 시스템 복구, 위험관리, 전문 자문 관련 비용으로 약 1억 3,130만 파운드가 기록되었다.

초기 침투 과정에서 IT 지원 조직을 이용한 사회공학 공격 가능성이 보도되었지만, 회사의 공식 자료만으로 모든 공격 단계를 확정할 수는 없다.

### 공격 경로

언론과 보안 분석에서 제시된 가능한 경로는 다음과 같다.

```text
제3자 지원 조직 대상 사회공학
    ↓
인증정보 또는 접근 권한 탈취 가능성
    ↓
기업 내부 시스템 접근
    ↓
주요 IT 환경 침해
    ↓
랜섬웨어 및 운영 시스템 장애
    ↓
온라인 주문 중단·업무 수동 전환
```

### 피해

- 온라인 주문 중단
- 운영 업무의 수동 전환
- 공급·물류·고객 서비스 장애
- 시스템 복구 및 조사 비용
- 매출과 기업 신뢰도에 대한 영향

### 기업 대응

- 시스템 격리
- 외부 보안 전문가 투입
- 업무 연속성 계획 가동
- 일부 업무 수동 운영
- 시스템 복구 및 단계적 서비스 재개
- 위험관리·보안 통제 강화

### 아키텍처 반영 — CTRL-06: Operational Resilience

**설계 근거:** 관리 플랫폼이 중단되더라도 이미 운영 중인 고객 서비스가 함께 중단되어서는 안 된다.

**적용 통제**

1. 제어면과 고객 서비스 실행면의 수명주기를 분리한다.
2. 제어면 장애로 기존 애플리케이션을 자동 종료하지 않는다.
3. 이전 중단 상태를 영속 작업 원장에 기록한다.
4. 새 배포 실패로 기존 리비전과 백업을 삭제하지 않는다.
5. 복구에 필요한 자산의 삭제 권한을 분리한다.
6. 별도 환경에서 데이터 복원 드릴을 수행한다.
7. 복구 완료는 HTTP 응답뿐 아니라 실제 데이터와 업무 기능으로 검증한다.
8. 침해된 자격증명과 에이전트를 폐기해도 독립 운영 가능한 서비스를 유지한다.

**검증 시나리오**

제어면 프로세스와 Worker를 중단하고, 고객 애플리케이션의 기존 서비스가 계속 동작하는지 확인한다.

**성공 기준:** 제어면 장애가 관리 대상 서비스의 즉각적인 운영 중단으로 연결되지 않아야 한다.

**참고:** M&S 2026 연차보고서, 공식 사고 발표 및 보안 분석

## 3.7. Cloudflare 대규모 DDoS 관측 사례

**기간:** 2025년  
**공격 유형:** 대규모 네트워크 DDoS, 봇넷, HTTP 요청 폭주

### 사건 개요

Cloudflare는 Aisuru/Kimwolf 관련 대규모 DDoS 공격 활동을 분석했다.

2025년 관측 데이터에는 최대 31.4Tbps 규모의 공격과 연간 약 4,710만 건의 DDoS 공격이 포함되어 있다.

이는 Cloudflare가 관측하고 방어한 공격 규모이며, Cloudflare 서비스 전체가 동일한 규모로 마비되었다는 의미는 아니다.

### 공격 경로

```text
공격자
    ↓
봇넷 및 다수의 공격 출발지
    ↓
대량 네트워크 패킷·HTTP 요청
    ↓
공개 서비스 엔드포인트
    ↓
네트워크·연결·애플리케이션 자원 소모
    ↓
서비스 지연 또는 가용성 저하 위험
```

### 아키텍처 반영 — CTRL-07: Layered Availability Defense

```text
인터넷
    ↓
CloudFront + AWS Shield + AWS WAF
    ↓
ALB / API Gateway
    ↓
인증·인가
    ↓
Rate Limiter
    ↓
작업 관리자
    ↓
SQS
    ↓
제한된 동시성의 Worker
```

**적용 통제**

- CDN과 DDoS 완화 기능 활용
- WAF의 HTTP 공격 차단
- 공개 오리진 우회 접근 제한
- 사용자·조직·IP별 호출량 제한
- 작업별 동시 실행 제한
- 큐 길이와 대기 시간 관리
- 고비용 작업의 사전 승인
- AI 호출 및 리허설 VM 생성 예산 제한
- 장애 상황의 요청 차단 및 회복 정책
- 자동확장 비용 폭주 방지

**검증 시나리오**

격리된 테스트 환경에서 API 요청을 증가시켜 Rate Limit, 큐, Worker 제한이 실제로 작동하는지 확인한다.

**성공 기준:** 요청량 증가가 무제한의 인프라 생성이나 비용 증가로 연결되지 않아야 한다.

**참고:** Cloudflare 2025년 4분기 DDoS Threat Report

## 3.8. Anthropic AI 자동화 첩보 캠페인

**발견:** 2025년 9월  
**공개:** 2025년 11월 13일  
**공격 유형:** AI 기반 자동화 공격, 도구 오용, 정찰·침투·자격증명 수집

### 사건 개요

Anthropic은 AI 코딩 에이전트와 외부 도구를 활용해 약 30개 조직을 대상으로 공격 활동을 수행한 캠페인을 공개했다.

보고서에 따르면 일부 침해는 성공했으며, 공격자는 AI를 활용해 정찰, 취약점 분석, 공격 실행, 인증정보 수집, 정보 반출 작업을 자동화했다.

귀속 판단과 자동화 비율은 Anthropic의 조사 결과에 따른 것으로 구분해야 한다.

### 공격 방식

```text
공격 목표 설정
    ↓
AI에 작업을 작은 단위로 분할
    ↓
합법적인 보안 업무처럼 위장
    ↓
AI가 외부 도구 호출
    ↓
정찰·침투·인증정보 수집
    ↓
결과 분석과 후속 공격 자동화
```

### 핵심 위험

AI가 외부 도구를 호출할 수 있다면 모델 출력이 실제 시스템 변경으로 이어질 수 있다.

관리 플랫폼에서 AI가 광범위한 운영 권한을 보유할 경우 공격자는 모델을 조작해 클라우드 리소스를 변경하거나 데이터에 접근하도록 유도할 수 있다.

### 아키텍처 반영 — CTRL-08: AI Is Not an Authority

**설계 원칙:** AI는 운영 권한의 소유자가 아니라 분석과 변경을 제안하는 주체다.

```text
AI 분석 및 변경 제안
    ↓
구조화된 실행 계획 생성
    ↓
정책 엔진의 독립적 검증
    ↓
실제 대상·권한·위험 범위 확인
    ↓
승인
    ↓
승인된 작업 계약 검증
    ↓
제한된 실행 서비스 호출
    ↓
실제 결과·감사 증거 확인
```

AI가 생성한 명령이 문법적으로 올바르거나 모델이 안전하다고 평가했다는 이유만으로 실행해서는 안 된다.

**검증 시나리오**

AI가 정상적인 마이그레이션 계획에 승인되지 않은 DB 삭제 또는 외부 데이터 전송을 포함하도록 유도하는 안전한 시험을 실시한다.

**성공 기준:** 독립적인 정책 엔진이 비인가 작업을 거부해야 한다.

**참고:** Anthropic의 2025년 AI-orchestrated cyber espionage 사례 분석

## 3.9. GitHub MCP 및 AI 코딩 에이전트 Prompt Injection

**관련 연구:** 2025년 GitHub Issue/MCP 기반 간접 프롬프트 인젝션 연구 및 OWASP AI 보안 지침  
**공격 유형:** Indirect Prompt Injection, Tool Misuse, Data Exfiltration

### 공격 개요

공격자가 AI의 시스템 프롬프트를 직접 변경하지 않더라도 AI가 읽는 외부 자료에 악의적인 명령을 삽입하여 도구 사용과 판단을 변경하려는 공격이다.

2025년 공개된 연구에서는 GitHub Issue 등 외부 콘텐츠가 MCP를 통해 AI에 전달되는 과정에서 비공개 정보 유출을 유도할 수 있는 위험이 제시되었다.

실제 피해가 확인된 침해사고와 실험 환경에서 재현된 취약점은 구분한다.

### 공격 경로

```text
공격자가 GitHub Issue 또는 README 수정
    ↓
비신뢰 자료에 명령형 텍스트 삽입
    ↓
AI 에이전트가 분석 작업 중 해당 자료 읽기
    ↓
외부 데이터 속 지시를 높은 우선순위의 명령으로 오인할 위험
    ↓
비인가 도구 호출 시도
    ↓
비밀 조회·데이터 전송·인프라 변경 위험
```

### 아키텍처 반영 — CTRL-09: Prompt Injection Containment

**Data Plane**
- GitHub Issue
- README
- 소스 코드
- 애플리케이션 로그
- 외부 웹페이지
- 도구 응답
- 사용자 제공 파일

**Authority Plane**
- 조직 보안 정책
- 명시적 사용자 승인
- 실행 권한
- 허용된 작업 계약
- 신뢰된 정책 버전

Data Plane의 내용은 Authority Plane을 수정하거나 권한을 부여할 수 없다.

### AI 도구 권한 정책 예시

```yaml
agent_policy:
  model_authority: advisory_only

  tools:
    read_source:
      allowed: true
      scope: current_application

    propose_patch:
      allowed: true
      workspace: isolated_copy

    inspect_resources:
      allowed: true
      scope: approved_inventory

    deploy:
      allowed: false
      delegated_to: execution_controller

    read_raw_secrets:
      allowed: false

    arbitrary_shell:
      allowed: false

  external_content:
    trust_level: untrusted
    may_grant_permission: false

  execution:
    require_policy_validation: true
    require_approved_plan_digest: true
```

위 YAML은 제안 정책 계약이며 특정 구현체의 공식 문법은 아니다.

**검증 시나리오**

README에 운영 DB 삭제를 지시하는 비신뢰 텍스트를 삽입한 후 AI가 이를 읽게 한다.

**성공 기준:** AI의 출력에 위험한 작업이 포함되더라도 실제 실행 정책에서 차단되어야 한다.

**참고:** GitHub MCP Prompt Injection 관련 공개 연구, OWASP LLM/Agentic AI 보안 자료

# 6. 실행 계약 및 권한 통제

## 6.1. 실행 계약 구조

실행 계획은 설명문이 아니라 검증 가능한 구조화 데이터로 표현한다.

```json
{
  "schema_version": "1.0",
  "operation_id": "op-example-001",
  "organization_id": "org-a",
  "application_id": "app-a",
  "operation": "deploy_revision",
  "target": {
    "provider": "aws",
    "account_id": "approved-account",
    "region": "ap-northeast-2",
    "resource_id": "approved-service"
  },
  "artifact": {
    "image_digest": "sha256:<verified-digest>"
  },
  "constraints": {
    "allow_resource_deletion": false,
    "allow_public_database": false,
    "max_new_resources": 3,
    "requires_rehearsal": true,
    "requires_approval": true
  },
  "preconditions": {
    "expected_current_revision": "rev-previous",
    "policy_version": "security-policy-v1"
  }
}
```

자리표시자는 실제 실행 전 검증된 값으로 교체해야 한다.

## 6.2. 실행 계약 검증 항목

- 조직·애플리케이션 ID
- 요청자 신원
- 승인자 신원
- 작업 종류
- 대상 클라우드 계정
- 대상 리전
- 대상 리소스
- 이미지 digest
- 허용된 변경 범위
- 리허설 결과
- 승인 계획 해시
- 승인 유효기간
- 정책 버전
- 현재 리소스 버전
- 작업 실행 lease·fencing 상태

## 6.3. 승인 및 실행의 분리

```text
변경 요청
    ↓
구조화된 실행 계획
    ↓
정책 검증
    ↓
리허설
    ↓
계획 해시 확정
    ↓
승인
    ↓
실행 시 정책·대상 재확인
    ↓
제한된 권한 발급
    ↓
실제 변경 실행
    ↓
결과·감사 증거 확인
```

### 중요한 실행 원칙

**승인된 계획과 실행할 계획은 동일해야 한다.**

승인 후 대상 계정, 이미지, 리소스, 정책 버전이 변경되면 재검증 또는 재승인이 필요하다.

**외부 API의 결과가 불확실한 경우 자동 재시도하지 않는다.**

AWS가 변경 요청을 받았지만 응답이 유실된 경우 실제 상태를 확인하기 전 동일 변경을 다시 실행하면 중복 리소스나 데이터 손상이 발생할 수 있다.

**운영 변경과 복구 자산 관리 권한을 분리한다.**

일반 배포 역할이 이전 리비전, 백업, 감사 증거를 임의로 삭제할 수 없어야 한다.

| POL-11 | 승인 당시 대상 상태 변경 시 재검증 |
| POL-12 | AI 출력만으로 권한·대상·정책 변경 금지 |

## 7.2. OPA/Rego 예제

```rego
package security.execution

default allow := false

allow if {
    input.operation == "deploy_revision"
    input.organization_id == input.identity.organization_id
    input.target.account_id == input.approval.account_id
    input.plan_digest == input.approval.plan_digest
    input.policy_version == input.approval.policy_version
    input.rehearsal.status == "passed"
    input.resource_state.revision == input.preconditions.expected_current_revision
    not input.constraints.allow_resource_deletion
    not input.target.database.publicly_accessible
    input.approval.valid == true
    input.execution_lease.valid == true
}
```

실제 환경에서는 정책 입력의 출처를 검증하고, 승인 서명·만료·신원·정책 버전·동시성 조건을 별도로 처리해야 한다.

일반 배포, 데이터 이전, 운영 리소스 삭제, 긴급 복구는 위험도가 다르므로 작업 유형별 정책으로 분리한다.

## 7.3. 역할 분리

| 역할 | 허용 작업 | 제한 |

## 8.4. 롤백 설계

**트래픽 롤백과 데이터 롤백은 동일하지 않다.**

트래픽 전환 이후 목적지 DB에 새 쓰기가 발생했다면 DNS나 로드 밸런서만 이전 대상으로 복구하는 방식은 데이터를 손실시킬 수 있다.

따라서 다음 조건을 구분해야 한다.

- 새 목적지에 쓰기가 발생하지 않은 경우
- 새 목적지에 쓰기가 발생한 경우
- 원본과 목적지에 동시에 쓰기가 발생한 경우
- 복제 상태가 불확실한 경우
- 스키마 변경이 비가역적인 경우

비가역적 변경이나 데이터 분기가 발생했다면 단순 자동 롤백을 허용해서는 안 된다.

복구 절차에는 다음을 포함한다.

1. 쓰기 주체 확인
2. 마지막 정합성 확인 시점
3. 복제 위치 및 지연
4. 양쪽 데이터 변경 여부
5. 역방향 동기화 가능성
6. 복구 대상 데이터의 일관성
7. 복구 승인
8. 실제 검증

일반적인 비동기 복제만으로 절대적인 RPO=0을 보장할 수는 없으며 실제 측정과 전환 통제가 필요하다.

### A. AI Prompt Injection 방어

- 조직 B의 클라우드 리소스 접근 시도

- 실제 리소스와 내부 작업 원장 비교

### D. 데이터 정합성 실패

- 목적지 데이터 누락 또는 지연 발생
- 정합성 검사 실패

- 원본 서비스 정상 유지

# 13. 최종 보안 설계 원칙

## 13.1. 침해는 발생할 수 있다는 전제

단일 방어 수단이 실패해도 다른 환경으로 피해가 확대되지 않아야 한다.

## 13.2. AI는 권한 주체가 아니다

AI가 분석·수정·계획을 수행할 수 있더라도 권한 발급과 운영 실행은 독립 정책과 승인 계약이 통제한다.

## 13.3. 정상 인증은 안전성을 보장하지 않는다

유효한 OAuth 토큰이나 클라우드 임시 자격증명을 사용하더라도 요청의 조직·앱·작업 범위를 확인한다.

## 13.4. 빌드 환경은 신뢰하지 않는다

사용자 소스·의존성·외부 스크립트 실행은 별도의 격리 환경에서 처리하고 운영 자격증명을 제공하지 않는다.

## 13.5. 미확인 상태는 성공이 아니다

클라우드 API 응답 유실, 작업 중단, 복제 상태 불확실성 등은 별도 재확인 과정을 거친다.

## 13.6. 복구 자산은 변경 권한으로부터 보호한다

운영 배포 역할이 감사 기록·백업·기존 리비전을 임의로 삭제할 수 없어야 한다.

## 13.7. 마이그레이션 완료는 실제 상태로 판정한다

이전된 시스템이 실행 중이라는 사실만으로 완료하지 않고 기능·데이터·보안·운영 지표를 확인한다.

## 13.8. 복구 가능성은 실제 시험으로 증명한다

스냅샷 존재, 배포 이력, 롤백 API 제공만으로 복구 가능성을 주장하지 않는다.

별도 환경에서 실제 복원과 데이터 검증을 수행한다.

# 14. 결론

최근의 사이버 침해사고는 공격 수단이 다양하더라도 공통적인 확산 경로가 존재한다는 사실을 보여준다.

```text
초기 침투
    ↓
계정·토큰·권한 확보
    ↓
내부 시스템 접근 확대
    ↓
데이터·운영 자산 통제
    ↓
유출·변조·파괴·서비스 중단
```

멀티클라우드 관리 플랫폼은 여러 운영 환경의 중앙 제어 권한을 가지므로 이러한 확산 경로를 제한할 수 있어야 한다.

따라서 본 아키텍처는 다음 세 가지를 핵심 보안 특성으로 정의한다.

**1. Compromise Containment**

일부 구성 요소가 침해되더라도 연결된 모든 클라우드 계정과 애플리케이션으로 피해가 확산되지 않도록 한다.

**2. Evidence-Based Execution**

AI의 판단이나 단순 API 성공 응답이 아니라 정책·승인·실제 리소스 상태·데이터 검증을 근거로 변경을 실행한다.

**3. Recoverable Migration**

운영 시스템 이전 중 장애가 발생해도 중복 실행·데이터 분기·백업 손상을 방지하고 검증된 복구 절차를 제공한다.

이 플랫폼의 목적은 WAF, EDR, SIEM, CSPM 등 개별 보안 제품을 모두 다시 구현하는 것이 아니다.

기존 클라우드 보안 서비스와 운영 통제를 통합하여 다음 질문에 검증 가능한 답을 제공하는 것이다.

> **현재 운영 시스템을 다른 환경으로 안전하게 이전할 수 있는가?**
>
> **이전 대상이 필요한 보안 정책과 데이터 보호 요구를 충족하는가?**
>
> **AI가 제안한 변경을 독립적으로 검증하고 승인된 범위에서 실행할 수 있는가?**
>
> **실행 실패 또는 침해 발생 시 데이터와 운영을 실제로 복구할 수 있는가?**

이를 위해 사고 분석, 위협 모델, 보안 통제, 실행 계약, 검증 시험, 감사 증거를 하나의 설계 체계로 연결한다.

# 부록 B. 향후 설계 문서 통합 기준

기존 보안 명세와 통합할 때 다음 구조를 사용한다.

| 항목 | 내용 |
|---|---|
| Threat ID | 공격·위협 식별자 |
| Incident Reference | 실제 침해사고 또는 연구 |
| Attack Path | 공격 진입점·권한 확대·피해 경로 |
| Affected Asset | 영향받는 시스템 |
| Security Goal | SG-1~SG-3 |
| Control ID | CTRL 및 POL |
| Trust Boundary | 외부·제어면·실행면·고객 환경 |
| Implementation | 기술 및 구현 위치 |
| Prevention | 사전 차단 방식 |
| Detection | 탐지·알림 |
| Response | 격리·폐기·복구 |
| Validation | 시험 절차 |
| Evidence | 로그·정책 결정·클라우드 상태 |
| Status | 설계·구현·검증 상태 |

기존에 정의한 통제 카탈로그 CC-01~12 및 실행 게이트 P0~P7, G6가 있다면 의미가 중복되는 항목을 통합하고 ID의 추적 가능성을 유지한다.
