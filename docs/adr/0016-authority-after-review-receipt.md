# ADR-0016: 감사 기록 이후 원본 권한의 최종 재검사

- 상태: 구현·단위 재현, 실제 PostgreSQL/TLS CI 검증 진행.
- 요구: SEC-PATCH-05·09·10, CTRL-01·04, POL-09·11, SG-2.
- 플랫폼 기준: `a610bbfb60d3a633597d75dc6e070addd3c3b559`. wire/TTL/실행기 계약 변경 없음.

## 확인한 틈

기존 endpoint는 원본 프로그램 검증을 끝낸 뒤 감사 기록을 쓰고 신원·등록을 재확인했다.
감사 쓰기 도중 **근거 삭제·검증자 신뢰 철회·새 보류**가 발생하면 원본/보류를 다시 보지 않아
직전 PASS가 반환될 수 있었다. 위 세 상황의 회귀 시험은 변경 전 모두 실패했다.

## 선택

`SecurityProgramService.review`에 선택적인 `record_review` callback을 추가한다. 반환은 정확한
`True`여야 한다. 기존 직접 소비자는 callback을 생략할 수 있어 API 호출 형태를 유지한다.
네트워크 endpoint는 반드시 callback으로 receipt를 기록한다.

1. 현재 프로그램·전체 근거를 읽고 인증/인가/보류를 확인한다.
2. 판정 후보를 만들고 endpoint가 신원·등록 확인, durable receipt, 신원·등록 재확인을 수행한다.
3. 프로그램 서비스가 **현재 프로그램·보류·근거 전체·서명·신뢰 철회**를 최종 재검사한다.
4. 시간 경과로 판정 내용/기한이 달라지면 거부한다. 성공할 때는 기록한 후보와 동일한 report를 반환한다.

마지막 원본 검사의 위치를 옮기므로 기존 3회의 collection을 늘리거나 인증 cache를 추가하지
않는다. endpoint는 callback이 한 번 기록한 digest와 반환 report의 digest가 같은지 확인한다.
감사 지연 때문에 report의 reviewed_at이나 원래 최대 5초 유효기간을 새로 늘리지 않는다.
`computed` 뒤에 최종 검사 실패로 `rejected`가 기록될 수 있다. computed는 전달/접수/실행 완료가 아니다.

## 검증과 한계

- 단위 재현: 감사 callback에서 근거 삭제·신뢰 철회·hold 추가 → 반환 거부.
- 정상 지연: 기록한 report digest와 반환값 일치, 최초 요청의 5초 기한 보존.
- 실제 PG/TLS: fsync receipt 후 별도 writer가 verifier를 철회하거나 hold를 commit → 반환 거부.
- 기존 직접 소비와 실제 T10/Sova의 현재 승인·계획 잠금·단일 접수 시험을 그대로 반복한다.

서로 다른 저장소·신원 공급자·호스트 실행기 사이의 분산 원자성은 제공하지 않는다. 최종 관측
직후의 철회 및 응답 전달 이후 변경까지 제거했다고 주장하지 않는다. 운영의 즉각 차단은 기존
호스트 plan lock 아래 hold/fencing과 실행기 권한으로 처리하며, 이 변경은 감사 중 생기는
이미 확인 가능한 변경을 놓치던 구간을 좁힌다. 서비스는 여전히 실행 권한이 없다.
